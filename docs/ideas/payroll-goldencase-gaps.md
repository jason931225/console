# Payroll golden-case gap register

Status: AUDIT — coverage gaps for professional review. Asserts no Korean legal conclusion.

A licensed professional's approval covers the cases that were submitted to them, and nothing else. This
register exists to find the cases that were not — so the next review is scoped by evidence rather than by
whichever example happened to be written first.

Every entry below is a **case**, what the **code does today** (file:line), and **the question a 노무사 or
세무사 must answer**. Where an auditor supplied a legal conclusion, it was converted into a question and
that conversion is noted. Korea's six controls in `docs/program/console-jurisdiction-register.json` are
`release_disposition: HOLD`; this register does not change that, and nothing here is a determination of
Korean law. `CTRL-KR-WORKFORCE-001` remains HOLD.

Raw findings from four audit axes: 48. After deduplication across axes: **19 blocking, 20 major, 1 minor**,
plus one blocking mechanism gap surfaced during citation verification (M-07).

## 2. Blocking gaps

Ordered so the ones that cap what any approval can achieve come first.

### B-01 — No pay-item model: one scalar gross is every insurance basis
*(merges three findings: excluded-paytypes, insurance-edges, tax-and-wage)*

**Case.** An employee is paid 기본급 2,800,000 + 식대 200,000 + 차량유지비 200,000. Or a 연차수당, 주휴수당,
소급 인상분 or 상여 is present in the imported source for a payroll line.

**Code today.** `extract_source_amounts` reads exactly one earnings figure,
`payroll.monthly_gross_pay_won` (`backend/crates/payroll/adapter-postgres/src/lifecycle.rs:444`).
`LineCalculationInput` carries exactly one amount field, `gross_won`, plus an optional pension basis
(`backend/crates/payroll/domain/src/lib.rs:670-675`). `employee_deduction_lines` then applies the
건강보험, 장기요양 and 고용보험 ppm rates to that same `monthly_remuneration_won` argument, and — when
`pension_standard_monthly_income_won` is `None` — to the pension basis as well
(`domain/src/lib.rs:741-761`). There is no pay-item type in the crate, only `DeductionLine`
(`domain/src/lib.rs:112-117`), and no 통상임금/taxable/insurance-basis flag exists anywhere in `backend/`
(grep for `비과세`/`non_taxable` over `backend/`: no hits).

**What breaks.** Whatever the importer folded into that one number is charged all four insurances with no
record of what it contained; anything the importer left in a sibling JSON key is silently dropped and never
reaches the payslip. Neither outcome is visible in the stored `payroll_line_calculations` row. Only 국민연금
has an escape hatch, and it is unvalidated against gross. The golden-case contract's required "all pay items
with 통상임금/taxable/insurance basis flags" (`docs/specs/payroll.md:63`) has no representation in any
struct, so the contract cannot be expressed by the code it governs.

**Ask.** 1a-1, 1a-5, 1b-10.

### B-02 — The gate cannot be scoped to a pay type or an employee category
*(merges three findings)*

**Case.** A run whose lines contain a 연차수당, a 소급분, a 일용직, a mid-month joiner or a 육아휴직 month is
issued under a release gate signed for the plain regular-monthly case.

**Code today.** Spec gate condition 2 is per pay type — "at least one matching golden case for the pay type
being enabled" (`docs/specs/payroll.md:76`). `GoldenPayrollCase` has four fields: `case_id`,
`rate_table_version`, `professionally_validated`, `expected_total_employee_deductions_won`
(`domain/src/lib.rs:187-192`). No pay type, no employee category, no employment status, no pay period, no
pay items. `validate_release_gate` checks only: non-empty version string, non-empty URL list, non-empty case
list, each case's version equals the gate's own declared version, the `professionally_validated` bool, a
present `ProfessionalValidation`, a 64-char hex digest, and a non-blank reviewer reference
(`domain/src/lib.rs:931-984`). No `pay_type` symbol exists anywhere in the tree. `parse_release_gate`
silently discards extra JSON keys on a stored case (`adapter-postgres/src/lifecycle.rs:1157-1192`).

**What breaks.** "Matching" is not expressible and is not evaluated. One signed case unconditionally
unlocks `load_payslip_issuance_in_tx` (`adapter-postgres/src/lifecycle.rs:1238`) for every pay composition
the org will ever run — including the pay types `docs/specs/payroll.md:52` explicitly excluded pending their
own golden cases. The per-pay-type condition is unenforceable as written.

**Ask.** 1c-1.

### B-03 — A golden case is a declaration, never executed
*(merges three findings)*

**Case.** A golden case declares `expected_total_employee_deductions_won`, a professional signs it, the gate
passes — while the kernel's arithmetic disagrees with the signed figure.

**Code today.** The field is declared at `domain/src/lib.rs:191` and never read by
`validate_release_gate` (`:931-984`, verified line by line). It is written once, parsed out of the gate JSON
at `adapter-postgres/src/lifecycle.rs:1183-1186`, defaulting to 0 when absent. Nothing anywhere compares it
to a computed `total_employee_deductions_won`; `validate_release_gate` never calls
`build_line_calculation` or `build_employee_payroll_draft`. The case is not even re-derivable: it carries no
gross wage, no pay date, no NTS row, no pension standard income, so no code now or later could recompute the
expectation from the record the reviewer signed.

**What breaks.** A golden case cannot fail. Any drift between the reviewed figure and the code is invisible
to the gate, to CI, and to the run-time gate in `validate_run_release_gate`.

**Ask.** 1c-2.

### B-04 — No golden case exists at all

**Case.** Every case named in this register has never been submitted to a licensed reviewer.

**Code today.** `docs/specs/payroll.md:58-69` specifies a twelve-element golden-case contract. The
repository contains no golden-case artifact of any kind — a search for `golden_cases` across `*.json`,
`*.sql` and `*.yaml` returns nothing. The only cases in existence are two in-crate test literals,
`golden-fixture-unvalidated` and `golden-fixture-professionally-reviewed`
(`domain/src/lib.rs:1287-1324`), whose `artifact_sha256` is the placeholder
`0123456789abcdef…` (`:1318`), plus one REST test fixture `GC-2026-06-A`
(`backend/crates/payroll/rest/tests/run_lifecycle_api.rs:787-796`).

**What breaks.** The professional-validation condition of the release gate has never been exercised against
real content. Every gap in this register is unvalidated, not merely uncovered.

**Ask.** 1c-1.

### B-05 — There is no way to register a validation

**Case.** A 노무사 reviews the golden cases and returns a signed validation memo. An operator wants to
register it so payroll can be released for the June run.

**Code today.** The gate is **read** from `payroll_draft_runs.legal_basis.release_gate` at
`adapter-postgres/src/lifecycle.rs:1139-1147`. Nothing in production writes that key. The 13 mounted routes
at `backend/crates/payroll/rest/src/lib.rs:121-176` contain no gate/validation registration endpoint
(close-preflight, close-attendance, calculate, exceptions, resolve, submit, decision, withdraw,
schedule-disbursement, disbursement/attest, issue-payslips, payslip-delivery, reads). A repo-wide search for
`release_gate` over `*.rs`/`*.sql`/`*.mjs` finds only the domain function, the adapter reader, one migration
comment, and the **test helper** `register_release_gate` — a raw
`UPDATE payroll_draft_runs SET legal_basis = legal_basis || $2` at `rest/tests/run_lifecycle_api.rs:782-808`.
`scripts/stage_coss_group_payroll_readiness.sql:49-70` writes `legal_basis` with readiness/blocker keys and
no `release_gate` key.

**What breaks.** The gate can only ever be satisfied by a hand-written UPDATE against the production
database — no actor attribution, no audit event, no permission check, no step-up, no revocation path. This
blocks every other gate finding from being fixable: nothing else about the gate matters until an approval can
reach it.

**Ask.** 1c-7.

### B-06 — Wages can be paid ungated; only the wage statement is gated

**Case.** An org closes June attendance, calculates, submits, approves (maker–checker), schedules a
disbursement, attests SUBMITTED_TO_BANK, then attests PAID — with no release gate registered at any point.

**Code today.** `validate_run_release_gate` has exactly one call site:
`adapter-postgres/src/lifecycle.rs:1238`, inside `load_payslip_issuance_in_tx`. Every upstream mutation
consults a raw status string instead: `calculate_run_in_tx` gates only on `run.status != "ATTENDANCE_CLOSED"`
(`:467-476`), then `submit_run_in_tx` (`:883`), `decide_run_in_tx` (`:910`),
`schedule_disbursement_in_tx` (`:1025`), and `attest_disbursement_in_tx` (`:1062-1128`, which flips the run
to PAID). `calculation_enabled` is never read in `lifecycle.rs` and is never set TRUE anywhere in the tree.
The integration test documents the ordering: PAID asserted at `run_lifecycle_api.rs:354-356`, first
`legal_gate` 409 at `:367-368`.

**What breaks.** The reachable failure mode is "wages paid off unvalidated amounts, wage statement withheld"
— the inverse of the spec sentence the CI gate greps for ("Production payroll calculations are disabled
unless all are true", `docs/specs/payroll.md:73`).

**Ask.** 1c-6.

### B-07 — Most of the golden-case contract has nowhere to go

**Case.** The hard case: a worker who joins on the 12th, is enrolled at two 사업장 in the same period, and
receives a retroactive adjustment settled in a later month.

**Code today.** Walking `docs/specs/payroll.md:60-67` field by field:
- **org/legal entity, 사업장** — `GoldenPayrollCase` has no org field (`domain/src/lib.rs:187-192`); a run is
  per `org_id` only (`migrations/0074_create_payroll_readiness.sql:5-26`); a line carries free-text
  `employee_company` (`0074:38`) used only as a sort key. No 사업장/사업장관리번호 entity exists for payroll.
- **pay period / pay date** — absent from the case, and a run period is forced to exactly one calendar month
  by `validate_close_prerequisites` → `is_exact_calendar_month` (`domain/src/lib.rs:349-355`, `:374-433`), so
  a partial period is unrepresentable.
- **employee category / employment status** — absent from both the case and `payroll_draft_lines`
  (`0074:31-60`).
- **pay items with basis flags** — no pay-item entity (see B-01).
- **retroactive adjustment** — no field, no table; the only correction mechanism is a new calculation
  `version` (`adapter-postgres/src/lifecycle.rs:486-491`).
- **expected employer costs, net pay, wage-statement fields** — the case carries only
  `expected_total_employee_deductions_won`.
- **per-case source URLs** — exist gate-wide only (`domain/src/lib.rs:205`).

**What breaks.** This converts every case the other findings surface from *unvalidated* into
*unvalidatable*. The reviewer has no place to record what they reviewed.

**Ask.** 1c-11.

### B-08 — Severance is live, spec-excluded, and emits a gross figure with no withholding path

**Case.** An employee with ≥1 year of service exits; the console emits a 퇴직금 figure for approval.

**Code today.** Severance is on the spec's Excluded-until-next-slice list (`docs/specs/payroll.md:52`), yet
it is reachable: `build_severance_pay_draft` (`domain/src/lib.rs:820-929`) is called from the exit-settlement
path at `backend/app/src/hr.rs:6942` and its result reaches a `READY_FOR_APPROVAL` status. The draft emits
`severance_pay_won` and the wage bases that produced it — and nothing else. `DeductionCode` is a closed
six-variant enum with no 퇴직소득세/지방소득세 variant (`domain/src/lib.rs:119-127`), and a repo-wide grep for
`퇴직소득` / `retirement_income_tax` / `퇴직연금` / `IRP` returns zero hits in `backend/`.

**What breaks.** The number presented for approval and hashed into the certification digest is unlabelled as
to gross-vs-net, and no code path could produce the net.

**Ask.** 1a-8, 1b-6.

### B-09 — 연말정산: a refund is unrepresentable, an over-charge is silently stored
*(merges two findings)*

**Case.** Year-end settlement lands on a February payslip — either as a refund, or as an additional charge
larger than that month's net.

**Code today.** Refund direction fails closed: both draft builders reject a negative income tax
(`domain/src/lib.rs:700-704`, and the same check in `build_employee_payroll_draft`), and
`payroll_line_calculations.total_deductions_won` carries `CHECK (total_deductions_won >= 0)`
(`migrations/0186_payroll_run_lifecycle.sql`), so a net-negative deduction total cannot be stored.
`DeductionCode` has no settlement variant (`:119-127`) and `deduction_code_str` is an exhaustive match over
the six (`adapter-postgres/src/lifecycle.rs:456-465`), so a new code is a compile error, not a data addition.
The opposite direction is silently wrong: `deduction_totals` uses `checked_sub`, which only fails on i64
overflow, never on deductions exceeding gross (`domain/src/lib.rs:805-818`), and `net_won BIGINT NOT NULL`
has **no** non-negative CHECK — while `gross_won` and `total_deductions_won` on the same table both do
(`0186_payroll_run_lifecycle.sql:51,56,57`). A negative net stores and the run continues to
`schedule_disbursement_in_tx` unchallenged. A grep for `연말정산`/`year_end` over `backend/` returns
nothing, and nothing enforces the spec's own exclusion: no run status, no blocker, no month check prevents a
February run being calculated, approved and issued as a plain month.

**What breaks.** One direction fails closed, the other is silently wrong. The error string "deductions exceed
gross wage" that appears to guard this is unreachable for negative results.

**Ask.** 1b-7, 1b-8.

### B-10 — Mid-month hire or termination: no proration, and the monthly 하한 is applied anyway
*(merges two findings)*

**Case.** An employee is hired on the 15th or terminated on the 20th and appears on that month's run.

**Code today.** A repo-wide grep for `prorat`/`PRORATION` over `*.rs`/`*.ts` finds only the unused
`'PRORATION'` value in the exception-kind CHECK (`0186_payroll_run_lifecycle.sql:79-80`); the only exception
`calculate_run_in_tx` ever creates is `OVERTIME_ALLOWANCE`
(`adapter-postgres/src/lifecycle.rs:604-627`). The run period cannot describe a partial month at all:
`is_exact_calendar_month` rejects anything that is not one whole calendar month
(`domain/src/lib.rs:374-433`). Neither `LineCalculationInput` nor the calculate SELECT carries a hire date, an
exit date, or a 자격취득/상실 date — the query reads only id, employee_id, display name,
`gross_pay_source_present`, `nts_tax_row_status`, `overtime_hours` and source row ids
(`adapter-postgres/src/lifecycle.rs:493-499`). And the pension basis is clamped **up** to the monthly
statutory minimum regardless of days worked:
`pension_standard_monthly_income_won.unwrap_or(monthly_remuneration_won).clamp(pension_limit.minimum_won, pension_limit.maximum_won)`
(`domain/src/lib.rs:741-744`).

**What breaks.** A mid-month joiner or leaver is indistinguishable from a full-month employee, receives a
full month of all four deductions, and a partial-month gross of e.g. 300,000 is rated as 410,000 with no
field by which the caller could state that this was a partial month.

**Ask.** 1a-12, 1b-3.

### B-11 — A zero or below-하한 month produces a deduction against no pay, and a negative net persists

**Case.** A month with zero or near-zero remuneration — full-month 육아휴직, 무급휴직, a hire on the last day
of the month, a mid-month exit before any pay accrues — reaches the calculator with gross 0.

**Code today.** The `.clamp(minimum_won, maximum_won)` at `domain/src/lib.rs:741-744` raises the pension
basis of a zero-pay employee to the 하한 (400,000 before 2026-07-01, 410,000 after —
`domain/src/lib.rs:568-581`), producing a positive 국민연금 deduction against zero gross. `deduction_totals`
then subtracts it with `checked_sub` (`:805-818`), so `net_won` becomes negative and is persisted — the table
constrains `gross_won >= 0` and `total_deductions_won >= 0` but leaves `net_won` unconstrained
(`0186_payroll_run_lifecycle.sql:51,56,57`). The only pension-limit test,
`caps_national_pension_basis_by_effective_limit` (`domain/src/lib.rs:1274-1284`), exercises the 상한 only; no
test drives the 하한 or a zero gross.

**What breaks.** A negative-net payslip reaches issuance with no blocker.

**Ask.** 1a-13.

### B-12 — 일용직 and short-time workers have no category

**Case.** A daily worker whose 4대보험 eligibility turns on days worked in the month and on weekly/monthly
hour thresholds.

**Code today.** The canonical employment type is constrained to REGULAR/CONTRACT/PART_TIME/INTERN
(`migrations/0172_create_employee_employment_profiles.sql:7`) — no daily category. The payroll calculation
input has no employment category at all (`domain/src/lib.rs:670-675`). The one datum that could drive a
days-worked threshold, `payroll_draft_lines.work_days`
(`migrations/0074_create_payroll_readiness.sql:42`), is not in the calculate step's SELECT list
(`adapter-postgres/src/lifecycle.rs:493-499`), so it cannot influence any deduction.

**What breaks.** The kernel emits the same four insurance deductions for a two-day-a-month day labourer as
for a permanent employee.

**Ask.** 1a-14.

### B-13 — 육아휴직 / 출산전후휴가 cannot even be recorded

**Case.** An employee on parental or maternity leave for all or part of a month.

**Code today.** The leave enumeration is `CHECK (leave_type IN ('annual', 'half_day'))`
(`migrations/0122_create_leave_requests.sql:29`, also enforced in the charge routine at
`0166_leave_exact_charge_and_home_branch.sql:904` and `:1029`) — such a period cannot be recorded, let alone
reduce or suspend a contribution. `employee_deduction_lines` builds a fixed six-element vector with no
eligibility or exemption parameter (`domain/src/lib.rs:763-802`); there is no code path by which any
insurance line can be omitted or reduced.

**What breaks.** Not representable at all, and compounds with B-11: a zero-gross leave month yields a
positive pension deduction and a negative net.

**Ask.** 1a-15.

### B-14 — A 간이세액표 row cannot be matched to the employee it is applied to

**Case.** An employee's row is attached from an import file. Nothing in the system knows that employee's
공제대상 가족 수, so a row looked up for a different family count is accepted and issued.

**Code today.** The kernel correctly refuses to synthesise brackets, but accepts any two non-negative
integers plus a non-blank version string as "the verified NTS row": `build_line_calculation` validates only
sign and non-blank version (`domain/src/lib.rs:694-728`), and `VerifiedNtsTaxRow` carries no employee
attribute (`:662-667`). `extract_source_amounts` reads three JSON keys and nothing else
(`adapter-postgres/src/lifecycle.rs:440-454`). A grep for `공제대상`/`dependent`/`family_count` over
`backend/` returns no payroll hit.

**What breaks.** A transposed or mis-keyed row flows straight into `payroll_line_calculations` and onto the
issued 급여명세서, with the version string stamped as provenance.

**Ask.** 1b-1.

### B-15 — The NTS table version is not effective-dated

**Case.** A run for a 2026 period is calculated using a 2024 간이세액표 row. The row's `table_version` says
so, and the calculation proceeds.

**Code today.** `table_version` is validated only as non-blank (`domain/src/lib.rs:705-709`); the DB CHECK is
`btrim(tax_table_version) <> ''` (`0186_payroll_run_lifecycle.sql`). No code compares the version to the run
period, the pay date, or any effective-dated registry of NTS editions — unlike the 4대보험 rates and pension
caps, which are effective-dated and selected by date (`EffectivePeriod`, `domain/src/lib.rs:24-39`;
`national_pension_base_limits`, `:567-582`). The version is then stamped verbatim onto the payslip payload as
the tax provenance field (`backend/crates/payroll/rest/src/lifecycle.rs:598`).

**What breaks.** The artifact looks sourced while being out of period.

**Ask.** 1b-2.

### B-16 — No pay date exists; `period_end` drives all rate and cap selection
*(absorbs the 2026-07-01 boundary finding)*

**Case.** The June 2026 payroll is paid on 10 July 2026.

**Code today.** There is no pay-date column anywhere in the payroll schema (`0074` and `0186` define
`period_start`/`period_end` only; a grep for `pay_date` over the migrations returns nothing). The lifecycle
adapter passes `pay_date: run.period_end` into the kernel
(`adapter-postgres/src/lifecycle.rs:547`). The kernel then keys everything on that one day:
`national_pension_limit_on(pay_date)` (`domain/src/lib.rs:741`) and every
`contribution_rate_on(…, pay_date)` (`:747-761`). The pension base limits genuinely change mid-year in the
kernel's own data — 400,000/6,370,000 through 2026-06-30, then 410,000/6,590,000 from 2026-07-01
(`domain/src/lib.rs:568-581`, with `EffectivePeriod::contains` exclusive of `to_exclusive`, `:36-38`). The
golden-case contract requires "pay period, pay date" as two distinct facts (`docs/specs/payroll.md:62`); the
schema can hold only one. `caps_national_pension_basis_by_effective_limit` (`:1274`) and the boundary test at
`:1164-1181` exercise `national_pension_limit_on` in isolation, but no test drives a run whose period end and
pay date fall on opposite sides of 2026-07-01.

**What breaks.** A June-period run can only ever use the pre-July band. Whichever date is the governing one,
the kernel can produce only one answer, and the caller cannot state the other.

**Ask.** 1a-19.

### B-17 — The minimum-wage guard is data with no comparator

**Case.** A part-time employee's issued payslip nets out below the 2026 minimum wage. Nothing in the system
says so.

**Code today.** `docs/specs/payroll.md:44` lists "Minimum-wage guard data for 2026" as in-scope, and the data
exists — hourly 10,320 / daily 82,560 / monthly-209h 2,156,880 (`domain/src/lib.rs:585-593`). But a
repo-wide grep for `minimum_wage_on` and `monthly_209h_won` over `*.rs` finds **only** the definitions
(`:87-93`, `:585-593`, `:612-617`) and one in-crate test call (`:1178`). Nothing compares it to gross, to
base_pay, to hours, or to a calculated line. "Guard" names data, not a check. The population is real:
`employee_employment_profiles.employment_type` admits PART_TIME and `base_pay NUMERIC(14,2)` carries no unit,
so the same column may hold an hourly or a monthly figure with no way to tell which
(`0172_create_employee_employment_profiles.sql:7-9`).

**Ask.** 1a-20.

### B-18 — The 급여명세서 payload lacks the prescribed fields

**Case.** A worker with 연장, 야간 and 휴일 hours receives a 급여명세서 that shows one gross figure and six
deduction lines.

**Code today.** MOEL guidance on required wage-statement fields is cited by the spec as part of this
contract (`docs/specs/payroll.md:29`, `:65`). What the code issues into the employee's vault is a nine-key
JSON payload — `run_id`, `line_id`, `period_start`, `period_end`, `gross_won`, `deductions[]`,
`total_deductions_won`, `net_won`, `tax_table_version`, `calculation_version`
(`backend/crates/payroll/rest/src/lifecycle.rs:590-601`), titled
`급여명세서 {period_start} ~ {period_end} · {employee_display_name}` (`:604-608`). No pay date, no employer
identification, no employee identifier as a field (the name appears only inside the title string), no
item-level pay breakdown, no hours, no per-item calculation method. `IssuanceLine` — the only fields
available to build it — is at `adapter-postgres/src/lifecycle.rs:1240-1268`.

**Ask.** 1a-21.

### M-07 — The domain lifecycle FSM has no production caller *(new; surfaced while verifying citations)*

**Case.** A reader — or a reviewer — reads `transition_payroll_run` and concludes that calculation is blocked

**Code today.** `transition_payroll_run` (`domain/src/lib.rs:296`) does contain those guards, and two tests
assert them: `calculation_is_blocked_without_persisted_validated_release_evidence` (`:1048`) and

**What breaks.** The FSM's guarantees — including the only in-crate mention of step-up in the payroll tree —

**Ask.** 1c-12.

## 4. Major gaps

### J-01 — 소급 정산 rated at the paying month's rates
Rates and caps are selected purely by the payment-side date: `contribution_rate_on(code, day)` and
`national_pension_limit_on(day)` (`domain/src/lib.rs:595-617`) are called with `pay_date`
(`:741-761`), and the adapter passes the *current* run's `period_end`
(`adapter-postgres/src/lifecycle.rs:547`). `LineCalculationInput` records no earned-for period. The pension
cap steps on 2026-07-01 (`:568-581`), so a retro payment across that boundary picks a different bound.
`DeductionCode` has no adjustment/refund variant (`:119-127`), and the `'RETRO_ADJUSTMENT'` exception kind
(`0186:79`) has no producer anywhere. → 1a-7, 1b-4.

### J-02 — 연차 미사용수당 is tracked in days, with no won column
`annual_leave_obligations` stores `leave_accrued`/`leave_used`/`leave_remaining` and has no amount column
(`0074_create_payroll_readiness.sql:70-86`). Its status enum admits `'PAYOUT_REVIEW_REQUIRED'` (`:78-79`),
but that value is only ever counted for a dashboard (`backend/app/src/hr.rs:1870`) and never written — the
only writer sets `USAGE_PROMOTION_DRAFT_REQUIRED` or `NEEDS_HR_REVIEW`
(`scripts/stage_coss_group_payroll_readiness.sql:246-250`). A repo-wide grep for
`연차수당`/`leave_payout`/`annual_leave_allowance` returns zero hits. A payout can therefore only reach a
payslip by being hand-folded into `monthly_gross_pay_won` — the silent-inclusion path of B-01. → 1a-6.

### J-03 — 주휴수당 is absent while 209 is hardcoded
A grep for `주휴`/`weekly_holiday`/`holiday_allowance` returns zero hits, yet two live numbers presuppose the
concept. `const MONTHLY_STANDARD_HOURS: i64 = 209` (`backend/app/src/hr.rs:6695`) divides monthly 통상임금
into the 통상일급 that feeds the live severance floor (`:6700-6718`), with no field recording the employee's
actual contracted hours — the code labels this a "STANDARD-WORKER ASSUMPTION (explicit, v1 scope)" at
`:6702`. And `minimum_wage_rates()` carries `monthly_209h_won` (`domain/src/lib.rs:590`) with no comparator
(B-17). → 1a-2.

### J-04 — The 평균임금 total is a bare scalar that gets hashed as fact
`SeverancePayInput.average_wage_total_won` is caller-supplied with no item breakdown
(`domain/src/lib.rs:145-146`), and the app layer requires only the period bounds, calendar days, that total,
and a free-text `pre_exit_three_month_wage_sources` field (`backend/app/src/hr.rs:6975-6983`). Nothing
apportions an annual 상여 or a 연차수당 into the window, and nothing flags which items were included — yet
the scalar is bound into the certification digest (`hr.rs:6720-6744`). A reviewer certifying the severance
figure is certifying a number whose composition the system never recorded. → 1a-9.

### J-06 — 파견/도급: a deduction line has no remitting entity
`DeductionLine { code, label_ko, amount_won, source_url }` (`domain/src/lib.rs:112-117`) carries no payer, no
사업장관리번호, and no distinction between employer of record and worksite. The nearest data is
`payroll_draft_lines.employee_company`, free-text NOT NULL used only in an index/sort
(`0074:38`, `:66`), and `employees.worksite_name`/`worksite_address`, free text from spreadsheet columns
(`0066_hr_core_employee_fields.sql:11-12,27-28`). No legal-entity or business-registration table exists in
`backend/crates/platform/db/migrations`. → 1a-18.

### J-07 — 다수 사업장: per-line clamping, no aggregation by employee
The calculate step iterates draft lines independently (`adapter-postgres/src/lifecycle.rs:508`), and the line
uniqueness key is `UNIQUE (org_id, run_id, employee_source_key)` — not employee
(`0074:59`) — so one person can legitimately hold two lines in one run. The 상한/하한 clamp is applied per
calculation call, i.e. per line (`domain/src/lib.rs:741-744`), and the 건강보험/고용보험 bases are never
combined. Nothing aggregates by `employee_id` and nothing flags the duplicate. → 1a-17.

### J-08 — 4대보험 정산 has no representable form
`DeductionCode` has exactly six variants (`domain/src/lib.rs:119-127`) and `deduction_code_str` is an
exhaustive match over them (`adapter-postgres/src/lifecycle.rs:456-465`), so a settlement code is a compile
error rather than a data addition. `total_deductions_won BIGINT NOT NULL CHECK (total_deductions_won >= 0)`
(`0186:56`) makes a net refund structurally unrepresentable. `RETRO_ADJUSTMENT` exists as an allowed
exception kind with no producer, its `amount_delta_won` is nullable by design (`0186:79-80`), and exceptions
never feed the persisted totals — so even the human-review escape hatch puts the money nowhere. → 1a-22.

### J-09 — 자격상실 신고: no 상실부호, no 보수총액, and no 취득 counterpart
`build_insurance_loss_payload` (`backend/app/src/hr.rs:7003-7027`) emits employee, exit date, reported reason
and the four form names — no loss reason code and no 보수총액. The generated EDI file requires both:
`loss_reason_code`/상실부호 and `annual_income_amount`/보수총액(원) are required columns
(`scripts/korean-connectivity/nhis-edi-loss-report.mjs:17`, `:22`), and `:41-46` rejects any row missing a
column key. The only fixture hardcodes `"01"` and `"0"`
(`docs/benchmarks/fixtures/korean-connectivity/nhis-edi-loss-report.fixture.json:14,19`) with no derivation
from any computed payroll. `scripts/korean-connectivity/` contains a loss-report generator only — the
자격취득 side of a hire has no artifact at all. → 1a-10.

### J-10 — No age or enrolment-status attribute exists
`contribution_rate_on(code, day)` takes only a code and a date (`domain/src/lib.rs:595-603`); there is no
parameter anywhere in the signature chain by which an employee attribute could change an employee-side rate
or suppress a line. `employee_ppm` is fixed for 국민연금 and 고용보험 (`:503-547`), and all six lines are
emitted unconditionally (`:763-802`). A grep for `birth_date`/`date_of_birth`/`age_band` over `backend/`
returns no employee attribute; there is no 임금피크제 notion of any kind. → 1a-16.

### J-11 — No passkey step-up on payroll mutations
Release-gate condition 6 requires passkey-signing active for run approval and pay-statement issuance
(`docs/specs/payroll.md:80`), and the G028 contract repeats it for approval, issuance, severance approval and
any correction that changes pay (`:96-98`). No `step_up`, `StepUp`, `passkey` or `webauthn` reference exists
anywhere in `backend/crates/payroll/rest/src/*.rs` (the only hit in the payroll tree is a *test name* in the
domain crate, `:1065` — see M-07). The mutating handlers enforce only org-wide RBAC plus audit:
`require_run_manage` → `authorize_org_wide(principal, Action::new(Feature::PayrollRunManage))`
(`rest/src/lifecycle.rs:41-43`), applied at `:191`, `:237`, `:319`, `:364`, `:401`, `:437`, `:477`, `:527`,
wrapped in `with_audits`. The mechanism exists elsewhere: `verify_step_up` at
`backend/crates/inbox/rest/src/lib.rs:150`. The CI gate asserts only that the phrase "passkey step-up" is
present in the spec file (`scripts/check-payroll-release-gate.mjs:35-39`). Today the employee acknowledging a
payslip needs a passkey while the employer approving and issuing it does not. → 1c-10.

### J-12 — Overlapping 연장/야간/휴일 hours cannot be represented, and only overtime is flagged
`payroll_draft_lines` stores `overtime_hours`, `night_hours` and `holiday_hours` as three independent
NUMERIC columns (`0074:44-46`) with no marker of whether they overlap. In the calculate step only
`overtime_hours` is selected (`adapter-postgres/src/lifecycle.rs:493-499`) and only it raises an exception
(`if overtime_hours.unwrap_or(0.0) > 0.0`, `:604-628`). There is no pay item, so no item can carry more than
one premium; the stacked amount, if any, is already baked into the imported gross scalar, unreviewed. → 1a-3.

### J-13 — 지방소득세 has no invariant against 소득세
The 지방소득세 line is taken verbatim from the supplied row and validated only as non-negative
(`domain/src/lib.rs:700-704`, `:790-801`); both amounts are read straight from `canonical_row`
(`adapter-postgres/src/lifecycle.rs:448-452`). Nothing relates it to the withheld 소득세 on the same line and
nothing checks its rounding unit. The spec is honest that this figure is supplied rather than computed
(`docs/specs/payroll.md:43`) — which leaves a transcription error indistinguishable from a source figure, on
a line deducted from an employee's pay. → 1b-5.

### J-14 — No residency, nationality or treaty attribute
A grep for `nationality`/`non_resident`/`resident_status`/`visa`/`외국인` over `backend/` returns no employee
attribute of any kind. The single 간이세액표 row path (`domain/src/lib.rs:733-803`) is the only withholding
path in the kernel and is selected and validated without reference to residency. Such a case is not merely
uncomputed but indistinguishable from a resident case at every layer, including the issued payslip. → 1b-9.

### J-15 — The artifact hash is not bound to content or to a calculation version
`validate_release_gate` checks only `artifact_sha256.len() != 64` and ascii-hex
(`domain/src/lib.rs:970-979`); nothing in the tree hashes or stores an artifact body. Issuance selects
`DISTINCT ON (c.line_id) … ORDER BY c.line_id, c.version DESC`
(`adapter-postgres/src/lifecycle.rs:1239-1247`) — the newest calculation — while `calculate_run_in_tx` bumps
`version` freely (`:486-491`) and never touches `legal_basis`. So a gate registered before a correction
releases the amounts produced after it. The repo contains the correct pattern one crate over:
`certified_package_digest` is recomputed at read time and CERTIFIED is downgraded to UNCERTIFIED_DRAFT on
mismatch (`backend/app/src/hr.rs:7115-7143`), backed by a covered-column trigger
(`0094_settlement_certification_trigger.sql:65-93`) and a DB shape CHECK
(`0093_settlement_certification.sql:41-56`). The payroll gate has none of the three. → 1c-5.

### J-16 — Reviewer identity is gate-wide, not per case
`docs/specs/payroll.md:67` requires per case "professional reviewer kind (labor_attorney, tax_accountant, or
equivalent licensed reviewer), reviewed date, and artifact hash". In code,
`GoldenPayrollCase.professionally_validated: bool` (`domain/src/lib.rs:190`) is the only per-case reviewer
signal, and `PayrollReleaseGateInput.professional_validation: Option<ProfessionalValidation>` (`:207`) is
singular with one `reviewer_kind` (`:196`) and one `reviewed_on` (`:197`). `validate_release_gate` never
relates the two (`:957-984`). A case can read as validated while the gate's single artifact belongs to a
reviewer of a different discipline who never saw it. → 1c-9.

### J-17 — One URL satisfies "one official source per statutory item"
Condition 1 (`docs/specs/payroll.md:75`) covers five contribution items plus minimum wage plus the
withholding table. The entire check is `if input.official_source_urls.is_empty()`
(`domain/src/lib.rs:937-941`) over an unstructured `Vec<String>` with no per-item key (`:205`), parsed with
`filter_map(Value::as_str)` and defaulted to empty (`adapter-postgres/src/lifecycle.rs:1159-1168`).
`statutory_contribution_rates()` returns five items, plus `minimum_wage_rates()` (`:585`) and the NTS source.
The integration fixture registers exactly one URL and the gate passes

## 6. What this audit did NOT check, and how it sampled

**Method.** Four auditors on four axes — spec-excluded pay types, 4대보험 edge cases, tax and wage-statement
handling, and the contract/gate as a mechanism — each reading `backend/crates/payroll/{domain,adapter-postgres,rest}`,

merged entries carry both citations. Every citation in sections 2–5 was re-verified by direct read against the
current `main` (`f39ed0501`) before publication, which is how M-07 surfaced.

**Not checked — and therefore not cleared:**

- **Nothing was executed.** No `cargo`, no `buck2`, no test run — the audit environment prohibits it. Every
  claim is a static read. Claims labelled *code-path-untested* mean "no test drives this", established by
  reading the test module, not by running it.
- **`console-lanes/*` was not entered** and is out of scope.
- **Absence claims are grep-shaped.** An absence claim is only as strong as the search terms. Terms used:
  `prorat|PRORATION`, `주휴|weekly_holiday|holiday_allowance`, `연차수당|leave_payout|annual_leave_allowance`,
  `연말정산|year_end`, `퇴직소득|retirement_income_tax|퇴직연금|IRP`, `비과세|non_taxable`,

  `birth_date|date_of_birth|age_band`, `pay_type`, `step_up|StepUp|passkey|webauthn`, `pay_date`,
  `release_gate`, `payable`, `minimum_wage_on|monthly_209h_won`, `transition_payroll_run`. A concept
  implemented under a term not on this list would have been missed.
- **Arithmetic against the official sources was not verified.** Whether 4.75% / 3.595% / 0.4724% / 0.9% and
  the 400,000–6,370,000 / 410,000–6,590,000 bands match what NPS/NHIS/최저임금위원회 actually publish is a
